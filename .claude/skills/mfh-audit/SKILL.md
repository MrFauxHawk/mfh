# /mfh-audit

You are running a retroactive consistency sweep across the whole project — catching drift that's already accumulated, not just what changed in the current session. `/mfh-commit`'s own stale-doc check only looks at the diff about to be committed; this command looks backward across however much history the user wants covered.

This command is read-mostly and diagnostic-first: gather findings, present them grouped by category, and only act on what the user approves. Don't fix anything before Step 5.

**Step 1 — Establish scope:**
Ask via `AskUserQuestion`: "How far back should I look?" — **Since last week** / **Last 30 commits** / **Since the oldest open phase started** / **Entire project history** (its Other fallback covers a custom range).

If the user isn't sure, suggest a default based on `.mfh/state/built.md`'s most recent entry date, or the oldest **Started:** date among currently active phases in `.mfh/state/progress.md` — whichever is more recent, since that bounds "things that could plausibly have drifted since the last known-good checkpoint."

**Step 2 — Gather context:**
Read `.mfh/design/roadmap.md`, `.mfh/design/milestones.md`, `.mfh/state/progress.md`, `.mfh/state/decisions.md`, `.mfh/state/built.md`, every file in `.mfh/library/`, and list `.mfh/plans/`. Run `git log` over the scoped range (`--stat` or `--name-only` so file paths are visible) to see what actually changed. None of these reads depend on each other — issue them together across as few messages as possible instead of one at a time.

**Step 3 — Run the eight checks in parallel via subagents:**
The checks below (3a–3h) are independent and read-only — none depends on another's output, so run them as parallel subagents instead of working through them one at a time in this conversation. Use the `Agent` tool with `subagent_type: general-purpose` (each check involves cross-file consistency judgment, not simple lookup — not a fit for a read-only search agent) and send all eight in a single message so they execute concurrently; set `run_in_background: false` on each since Step 4 needs every result before it can proceed and there's nothing else to do meanwhile. This also keeps the raw file contents each check reads out of this conversation's context — only the findings come back.

A subagent has no memory of this conversation, so each prompt must be self-contained: give it the scoped range from Step 1 (dates or commit range), the exact file paths to read (a subagent can read files itself — don't paste full file contents into the prompt), and the judgment criteria below verbatim. Ask each to return a short structured list of findings (or an explicit "nothing found" if clean) rather than prose narration, so Step 4 can present results directly without re-deriving them.

**3a — Stale library docs:** For each file in `.mfh/library/`, note what area or concern it documents. Cross-reference against the files touched in the scoped git history (`git log` with `--stat` or `--name-only` over the scoped range). Flag a likely gap when a commit clearly touches an area a doc describes (schema, routes, shared components, conventions) but that doc's own last-touched commit is well before it — a new API route with nothing added to a routes/architecture doc, a schema field with the database doc untouched, a new shared component absent from a components doc. Use judgment, not exhaustiveness — this is the same check `/mfh-commit` runs on a single diff, just over a wider window, so the same "plausible gap, not everything adjacent" bar applies.

**3b — Orphaned or stray plan files:** List every file in `.mfh/plans/` and read `.mfh/state/progress.md`. For each plan file, check whether it matches the expected naming convention for an active phase (`m{N}-p{N}-plan.md`, `wi-p{N}-plan.md`, `{prefix}-p{N}-plan.md`) **and** whether that phase still has an open section in `progress.md`. Flag any plan file that:
- Doesn't match any currently active phase (the phase it belonged to was likely already closed by `/mfh-done`, or never matched the naming convention `/mfh-done` looks for and so was never cleaned up)
- Doesn't match the naming convention at all (typo, manual copy, one-off)

**3c — Stuck "ready to close" phases and unresolved verification:** Read `.mfh/state/progress.md`. Scan each active phase's Notes for repeated language indicating the work is done and just awaiting closure (e.g. "ready to close," "ready for `/mfh-done`," "phase ready for commit") across multiple dated updates without the phase ever actually being closed. Flag these explicitly — this is exactly the kind of thing that sits for weeks because nothing forces the closing step. Also check each phase's plan file (in `.mfh/plans/`) for an unchecked Verification Checklist on a phase whose tasks are otherwise all checked off — flag that too, since it means the described "done" state was never actually confirmed.

**3d — decisions.md references:** Grep `.mfh/state/progress.md` and `.mfh/state/built.md` for references to `decisions.md` (typically "See `decisions.md` → \"...\""). For each, confirm a matching heading/entry actually exists in `.mfh/state/decisions.md`. Flag any reference that doesn't resolve — it means either the entry was never written or was written under a different title than what's referenced.

**3e — roadmap.md drift:** Read `.mfh/design/roadmap.md` and `.mfh/design/milestones.md`. Compare roadmap.md's **Current Track**/**Current Focus** against what milestones.md actually shows as active — flag it if roadmap.md still names a milestone that's already fully shipped and moved to Completed Milestones, or doesn't mention a milestone that's clearly the active one. Check the **Goals** list for anything that reads as already achieved (cross-reference against `.mfh/state/built.md`) but is still phrased as aspirational. Check whether **Live Sections** (if present) is missing an app that a completed milestone shipped. This is the same category of drift as library docs, just at the project-vision level instead of the code level.

**3f — decisions.md content that belongs in a library doc:** Read `.mfh/state/decisions.md` in full (not just its most recent entries) and every file in `.mfh/library/`, then cross-reference every decisions.md entry against those library docs. Flag an entry when it states a durable, still-true rule, convention, or gotcha — not a one-off investigation narrative — that isn't reflected in any library doc: a tooling/lint decision nobody would discover without reading decisions.md end to end, a semantic rule (color, interaction, status-handling) that gets invoked as established in later entries but was never actually stated as a rule anywhere, a cross-cutting architectural rule missing from the doc that describes that flow. Don't flag narrative-only entries — investigation logs, rejected approaches, bug postmortems whose fix already lives in the code and needs no separate statement. Same bar as 3a: a plausible, load-bearing gap, not everything adjacent.

**3g — decisions.md archive-worthiness:** Check its size (`wc -l`) and section count (`grep -c '^## '`). This file is read in full by every `/mfh-execute` session, so unlike a normal doc, its size is a direct, recurring cost, not just clutter — flag it once it's grown large enough that a meaningful fraction of it plausibly no longer describes the current system. Skim section headers and content for signals worth surfacing before the user decides whether to approve a split: entries explicitly marked SUPERSEDED, phases with multiple dated "Round 1 / Round 2 / Round 3" style rewrites where only the last round still applies, or sections describing a feature/subsystem that's since been removed or fully replaced. Report a rough estimate ("looks like roughly N of the M sections are superseded") so the user can judge whether a split is worth doing right now, without actually performing the split yet.

**3h — built.md archive-worthiness:** Check its entry count (`grep -c '^## '`). Flag it once it's grown large enough that reading the whole file before any edit (required before every `/mfh-done` append) is carrying real weight. This one needs no relevance judgment — every entry already describes a fully-closed, shipped phase, so age is the only axis. Many MFH projects already have a precedent for this exact pattern worth checking for: a compressed "Backfilled History" section at the bottom of `built.md`, or a similarly-named archive file referenced from it — if one exists, note whether it's been kept up since, or whether it stopped after some point (a sign this maintenance pass used to happen manually and lapsed).

**Step 4 — Present findings:**
Take each subagent's returned findings and group them under clear headers (Stale Library Docs / Orphaned Plan Files / Stuck Phases / Unresolved Verification / Broken Decision References / Roadmap Drift / Decisions Better Suited to a Library Doc / decisions.md Due for Archiving / built.md Due for Archiving). For each finding, state what was found and why it's flagged — not just a bare file list. If a check came back with nothing, say so briefly rather than omitting it silently (an empty audit result should read as "checked and clean," not "not checked"). If a subagent's response doesn't clearly match the expected format, use judgment to slot it under the right header rather than dropping it.

Ask via `AskUserQuestion` (multi-select): "Want me to fix any of these now?" — one option per category that actually has findings, plus a **Fix everything** option and a **Fix nothing, just wanted the report** option — let the user pick individual categories rather than assuming all-or-nothing.

**Step 5 — Apply approved fixes:**
For each approved finding:
- Stale library doc → make the edit, following the compact-header convention where applicable
- Orphaned plan file → confirm before deleting (it may represent real unfinished work, not just cleanup)
- Stuck phase → don't force-close it yourself; tell the user to run `/mfh-done [phase]` once they confirm it's actually ready
- Unresolved verification → don't check items off on the user's behalf; surface it so they can walk it live or explicitly waive it
- Broken decision reference → either write the missing `decisions.md` entry (if the rationale is recoverable from context) or correct the reference
- Roadmap drift → make the edit directly (this is the same kind of update `/mfh-done` already makes automatically when a milestone completes — you're just catching up on one it missed)
- Decision belongs in a library doc → add the durable rule to the relevant doc, following its compact-header convention. This is additive, not a move — leave the original decisions.md entry in place (its surrounding *why*/context is exactly what an archive pass later needs to judge whether the entry is still load-bearing or purely historical).
- decisions.md due for archiving → the one fix here that takes real judgment, so slow down: read every section and classify it as either still load-bearing (describes the system, a convention, or a constraint as it exists today) or superseded/historical (an intermediate iteration a later entry explicitly replaced, an investigation whose conclusion is now fully reflected in code with nothing left to decide from reading it, a cancelled idea already reflected as such elsewhere). Move the historical sections — verbatim, unedited, same relative order — into `.mfh/state/decisions-archive.md` (create it if absent). `decisions.md` keeps only the load-bearing sections, plus a one-line pointer at the top of the file to `decisions-archive.md` for history. Never delete a section outright — after this, every entry lives in exactly one of the two files. Show the user the proposed keep/archive split before writing it if the file is large enough that a wrong call would be costly to undo.
- built.md due for archiving → mechanical, no relevance judgment needed. Keep the most recent entries in `built.md` (default to roughly the last 20, or whatever spans the last couple months at the project's actual pace — ask the user if genuinely unsure) and move everything older, verbatim and in the same order, into `.mfh/state/built-archive.md` (create it if absent). Since `built.md` is newest-first, each archive run's freshly-archived batch is newer than whatever's already in the archive file — prepend it to the top of `built-archive.md`, don't append to the bottom, so the archive file itself stays newest-first end to end.

Report what was fixed and what was left for the user to handle themselves.
